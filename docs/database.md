# Database

Postgres on **Neon**, accessed via **Drizzle ORM** using the `@neondatabase/serverless` HTTP driver. The driver matters: it's the only Postgres client that works inside serverless functions without exhausting connection pools.

## Connection

```ts
// db/index.ts
import { neon } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-http';
import * as schema from './schema';

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
```

One `db` instance is fine for the whole app — the HTTP driver creates a fresh connection per query.

## Schema

The full schema lives in `db/schema.ts`. Tables fall into three groups.

### Auth tables (managed by better-auth)

`users`, `sessions`, `accounts`, `verifications` — generated by the better-auth Drizzle adapter. Do not edit by hand. See [auth.md](./auth.md).

### `projects` (one row per broadcast event, created from the admin UI)

A project is a **broadcast event** created by the operator from the `/admin` gallery via **Add Project**. It is **not** a file-system folder. Each project selects one *overlay package* — a folder under `projects/` — through `project_label`. Many projects may reuse the same package (e.g. two `TCG` events on different dates). See [projects-system.md](./projects-system.md).

```ts
export const projectMode = pgEnum('project_mode', ['team_vs_team', 'player_vs_player']);

export const projects = pgTable('projects', {
  id: uuid('id').defaultRandom().primaryKey(),
  name: text('name').notNull(),                              // project_name
  mode: projectMode('mode').notNull(),                       // project_mode — drives bracket participant type
  label: text('label').notNull(),                            // project_label — overlay-package folder name under projects/
  pictureUrl: text('picture_url'),                           // project_picture — uploaded image URL
  eventDate: date('event_date'),                             // project_date
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});

export const createProjectSchema = z.object({
  name: z.string().min(1).max(120),                          // project_name
  mode: z.enum(['team_vs_team', 'player_vs_player']),        // project_mode
  label: z.string().min(1),                                  // project_label — validated against the live projects/ scan
  pictureUrl: z.string().url().optional(),                   // project_picture
  eventDate: z.string().date().optional(),                   // project_date (yyyy-mm-dd)
});
```

`label` must match an existing folder under `projects/`. The server validates it against a live directory scan on write — the same scan that populates the Add Project dropdown. There is **no longer** a `projects` row per folder: folders are templates, projects are instances. The retired `projects:sync` script is replaced by that scan; see [Migrations vs project creation vs overlay packages](#migrations-vs-project-creation-vs-overlay-packages).

### Entity tables (the data CRUD section manages)

Every entity follows the same pattern.

```ts
export const players = pgTable('players', {
  id: uuid('id').defaultRandom().primaryKey(),
  projectId: uuid('project_id')
    .notNull()
    .references(() => projects.id, { onDelete: 'cascade' }),
  name: text('name').notNull(),
  // ...entity-specific fields — see data-entities.md
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
}, (t) => ({
  byProject: index('players_project_idx').on(t.projectId),
}));
```

Tables in this shape: `players`, `teams`, `sponsors`, `assets`, `videos`, `brackets`, `project_css`, `rundowns`, `rundown_items`. Field-level reference per entity is in [data-entities.md](./data-entities.md).

`rundown_items` is special: it carries each title's per-instance configuration as a JSONB column.

```ts
export const rundownItems = pgTable('rundown_items', {
  id: uuid('id').defaultRandom().primaryKey(),
  rundownId: uuid('rundown_id')
    .notNull()
    .references(() => rundowns.id, { onDelete: 'cascade' }),
  projectId: uuid('project_id')                              // denormalized for direct filtering
    .notNull()
    .references(() => projects.id, { onDelete: 'cascade' }),
  titleKey: text('title_key').notNull(),                    // folder name under projects/<slug>/titles/
  position: integer('position').notNull(),
  data: jsonb('data').$type<Record<string, unknown>>().notNull(),  // validated against title's model.ts
}, (t) => ({
  byRundown: index('rundown_items_rundown_idx').on(t.rundownId, t.position),
}));
```

## Multi-tenancy: the `project_id` FK isolation pattern

This is the most important pattern in the codebase. **Read this section before adding any new entity.**

### The rules

1. **`projects.id` is a UUID** generated when the operator creates the project from the UI. (It used to be a text slug matching a folder; that changed when projects became UI-created event instances — see [projects-system.md](./projects-system.md).) The overlay-package folder is referenced separately by `projects.label`.
2. **Every entity table has a `project_id uuid not null references projects(id) on delete cascade` column.** No exceptions.
3. **Every index that supports a query starts with `project_id`.** Composite indexes like `(project_id, name)` are common because we always filter by project.
4. **Every query filters by `project_id`.** There is no `getAllPlayers()` — only `getPlayersForProject(projectId)`.
5. **All API routes live under `/api/projects/[projectId]/...`.** This enforces rule 4 structurally — the project ID is part of the URL, not a hidden query string.
6. **The server derives `projectId` from the URL, never from the request body.** Even validated bodies cannot move a row between projects:

   ```ts
   // app/api/projects/[projectId]/players/route.ts
   export async function POST(req, { params }) {
     const session = await auth.api.getSession({ headers: req.headers });
     if (!session) return new Response('Unauthorized', { status: 401 });

     const body = await req.json();
     const parsed = createPlayerSchema.parse(body);          // body MAY NOT contain projectId
     await db.insert(players).values({
       ...parsed,
       projectId: params.projectId,                          // URL is authoritative
     });
     return new Response(null, { status: 201 });
   }
   ```

7. **RTK Query tags include the project ID** so cache invalidation is scoped correctly: `{ type: 'Player', id: projectId }`. See [state-management.md](./state-management.md).

### Why this pattern, not schema-per-project

| | Shared tables + `project_id` | Schema-per-project |
|---|---|---|
| Drizzle types | One schema | Regen per tenant |
| Migrations | Run once | Run N times, can drift |
| Adding a project | Insert one row | Migrate to create N tables |
| Cross-project reports | Trivial | UNION across schemas |
| Isolation guarantees | App-level (must filter) | DB-level |

Multi-tenancy bugs are mitigated by **routing every query through `/api/projects/[projectId]/...`** — the filter is structurally enforced rather than a discipline to remember.

## Migrations vs project creation vs overlay packages

Three distinct operations. Conflating them is the most common source of confusion.

| | `npm run db:migrate` | Create a project (UI) | Add an overlay package (folder) |
|---|---|---|---|
| Affects | Schema (DDL) | One `projects` row (DML insert) | The file system only |
| When | Schema changes | Operator starts a new event | Developer ships new overlays/CSS |
| Run by | Developer / CI | Operator, from `/admin` | Developer, by adding `projects/<label>/` |
| DB change | Yes (tracked migration) | One insert via the API | None (discovered by directory scan) |

> The old `projects:sync` script (folder → `projects` row) is **gone**. Projects are now created in the UI; overlay-package folders are discovered by scanning `projects/` at request time. See [projects-system.md](./projects-system.md).

### When you need a migration

- Adding a new entity table (e.g., `commentators`).
- Adding, removing, or renaming columns on existing tables.
- Changing relationships, indexes, or constraints.

Workflow: edit `db/schema.ts` → `npm run db:generate` → commit the generated `.sql` → `npm run db:migrate` against the right `DATABASE_URL` (dev then prod, never as part of `next build`). See [deployment.md](./deployment.md#migrations-workflow).

### When you do NOT need a migration

- **Creating a project.** It's a `projects` row inserted by the API when the operator clicks Add Project.
- **Adding a new overlay package folder.** Pure file-system change; discovered by the directory scan.
- **Adding a new overlay to a package.** Overlay (title) data is stored in `rundown_items.data jsonb`; no schema change.
- **Editing an overlay's `model.ts` or `settings.ts`.** Validated at the API boundary / read from the registry, not the database.
- **Swapping fonts or editing `project.css`.** File-system change only.

### Action → command table

| Action | `db:migrate`? | DB write? | File-system change? |
|---|:-:|:-:|:-:|
| Create a project (Add Project) | ❌ | ✅ (one row) | ❌ |
| Add a new overlay package folder | ❌ | ❌ | ✅ |
| Add a new overlay to a package | ❌ | ❌ | ✅ |
| Edit `project.css` / swap fonts | ❌ | ❌ | ✅ |
| Add new CRUD entity (e.g., Commentators) | ✅ | ❌ | ❌ |
| Add a column to `players` | ✅ | ❌ | ❌ |
| Change an overlay's `model.ts` / `settings.ts` | ❌ | ❌ | ✅ |

## Drizzle CLI commands

```bash
npm run db:generate    # diff schema.ts vs migrations/ → emit a new SQL file
npm run db:migrate     # apply pending migrations to $DATABASE_URL
npm run db:studio      # open Drizzle Studio (browser DB inspector)
```

`drizzle.config.ts`:

```ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: './db/schema.ts',
  out: './db/migrations',
  dialect: 'postgresql',
  dbCredentials: { url: process.env.DATABASE_URL! },
});
```

## Naming conventions

- Table names: `snake_case`, plural (`players`, `rundown_items`).
- Column names: `snake_case` in the DB; Drizzle maps to `camelCase` in TS.
- FK columns: `<entity>_id` (`project_id`, `rundown_id`).
- Indexes: `<table>_<columns>_idx`.
- Soft deletes: not used in MVP. Use `ON DELETE CASCADE` and rely on the audit log later.
